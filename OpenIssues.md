# Open Issues

- ~Toolbar icons still regress on GNUstep: the DateTracker-style toolbar baseline displays them, but GNUstep’s standard toolbar constrains rows to ~24 px so our 32 px art is clipped, and labels revert to the theme’s default colour if we re-enable the custom container.  
  **Resolution:** We now generate GNUstep-specific 24 px PNGs (light/dark + active variants) and load them before the 32 px masters, so the DateTracker baseline renders correctly without the custom container path (which has since been removed). The end-to-end workflow lives in `docs/ToolbarIconsOnGNUstep.md`.~
- ~Dark-theme toolbar regression on GNUstep: when Sombre is active (or Toolbar Theme = Dark) the stock toolbar sometimes renders blank icons/labels, matching the failing `ToolbarIconThemeProbe`.  
  **Resolution:** Replaced the toolbar art with Sombre-friendly PNGs, normalized every asset to 8-bit RGBA, disabled the GNUstep dark-theme filter, and relaxed the bitmap “visible pixel” check so GNUstep no longer discards the icons. Active/inactive variants now draw correctly. (`docs/ToolbarIconsOnGNUstep.md` captures the full workflow.)~
- ~Custom cursor glyphs missing on GNUstep: switching tools always leaves the system arrow cursor, so the pen/highlighter/text cursors never appear.  
  **Resolution:** Ensured the canvas becomes first responder, always accepts mouse-move events, keeps `mouseInsideCanvas` in sync, and gates custom cursors on actual hover state. Cursor assets now ship with the bundle, `CursorAssetProbe`/`CursorRectProbe` guard the path, and `scripts/run_cursor_debug.sh` verifies the tinted cursor logs.~
- ~Text popover layout still broken on GNUstep: the color swatches disappear under the “Sample Text” preview, and the preview area clips the swatch row.  
  **Resolution:** Rebuilt the popover layout so the swatches live inside a dedicated container view anchored under the color controls while the preview scroll view now sizes itself only within the remaining vertical space above the button row. On GNUstep this keeps the swatch rows visible regardless of popover height because the preview no longer forces a 140 px minimum that overlaps upstream content.~
- ~Text popover font selection does nothing: changing the font family or size in the popover never updates the preview or the actual text tool.  
  **Resolution:** Stopped calling `NSFont fontWithName:` using family titles (which returns nil on GNUstep) and now ask `NSFontManager` for a concrete face, falling back through the family’s available members before the default font path. Font size edits and family changes now yield real `NSFont` instances, so the delegate applies them immediately to both the preview and the canvas.~
- Text toolboxes render with opaque backgrounds: when inserting text, GNUstep draws a dark, opaque rectangle behind the text area. We want a transparent text box so it matches other platforms.  
  **Investigations so far:** Verified `NSTextView` uses its default background; even though we set it to clear in Cocoa, GNUstep ignores it. Need to ensure the text layer uses `drawsBackground=NO` and that our canvas compositing respects transparency.  
  **Theory of the case:** GNUstep’s `NSTextView` always draws its background unless we subclass or use `NSTextField` with custom drawing. Might require a GNUstep-specific path to skip the default fill.
- Preferences panel spacing is a mess: sections butt up against each other and controls overlap when the window is resized.  
  **Investigations so far:** The window uses manual frames plus nested boxes; on GNUstep the controls don’t respect our autoresizing masks. Need to audit `PreferencesWindowController` layout and switch to a vertical stack or Auto Layout constraints so the spacing stays consistent.  
  **Theory of the case:** Our Cocoa-only layout assumptions (baseline adjustments, segments) aren’t implemented in GNUstep, so the view tree needs explicit padding/margins. Using `NSGridView` or layout constraints per section should stabilize the spacing.
- Native tooltips resurfaced on GNUstep: instead of our custom tooltip controller, GNUstep shows the default yellow bubble (which is broken).  
  **Investigations so far:** We previously scrubbed native tooltips and registered views with `STToolbarTooltipController`, but after removing the custom toolbar code we may not be calling `applyToolTipToToolbarItem` consistently. Need to capture `debug.log` entries for tooltip registration and ensure `GSShowToolTips=NO` is still honored.  
  **Theory of the case:** Without the custom container views, GNUstep recreates native tooltips each time it builds the toolbar. We might need to refresh tooltip suppression after every toolbar rebuild or reintroduce a stripped-down tooltip controller.
- ~Color overlay badges sit at the top-right: the pen/highlighter/text toolbar icons display their color dot in the top-right instead of the previous bottom-right.  
  **Resolution:** Confirmed GNUstep’s `NSBitmapImageRep` coordinates originate at the top-left after switching to 24 px toolbar art, so the badge math drew the circle near the top-right. Flipped the badge’s Y coordinate in `imageByAddingColorBadgeToImage:` so the dot returns to the bottom-right while Cocoa continues using the existing drawing path.~
